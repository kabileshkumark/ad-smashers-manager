# Version 1.0 - Technical Build 1.0.25

Owner approved deployment on 24 October 2026 after local QA and an explanation of pending-change recovery. No commit or deployment preceded that approval.

## Root Cause And Scope

A catch-all save handler scheduled another save every five seconds without an attempt limit or error classification. Each save also reread the audit collection and rewrote unchanged records. During service quota exhaustion this amplified requests and presented a data-load failure as a sign-in failure.

The existing persistence implementation is corrected directly. No production override, alternate save path, new dependency or additional retry layer is introduced. The obsolete duplicate saveState definition is removed.

## Changes

- Quota exhaustion stops automatic saves immediately. Authentication remains available when authentication succeeds but the subsequent data request is limited.
- Transient network failures, timeouts and HTTP 408/500/502/503/504 allow at most three save attempts total, with five- and fifteen-second delays. Conflict recovery shares this budget and may reload at most once. Permanent errors and invalid responses do not enter a generic retry loop.
- Concurrent save calls join the same in-flight operation. New edits do not shorten retry delays or reset the budget. Sign-out cancels queued retries and late requests cannot change a new session's save metadata.
- Requests have a twenty-second deadline including body reads, with no transport-level retries. Repeated collection pagination tokens fail closed.
- Pending changes remain in the existing local journal. Successful explicit data recovery loads current cloud records and reapplies pending changes before saving. A failed recovery does not reset the retry budget. Normal reload starts a new user-initiated recovery cycle.
- A save clears only its matching pending snapshot after confirmation. An edit made during the save remains pending, including edits within the same millisecond. Missing commit acknowledgement does not clear the journal or advance the local revision.
- Delta saves write only changed records plus the atomic workspace revision and audit record. Unchanged saves make no requests. Audit reads are cached for one hour per authenticated session, and expired-audit deletion stays within the atomic write limit.

Session, attendance, court capacity, allocation, payment, Credit, Advance and activity business rules are unchanged. Existing stored records and the write-protocol version remain compatible. Browser-local pending changes are not a cloud backup: do not clear browser data while changes are unsynced.

## Verification

- 304 automated tests passed, covering existing app behavior and retry, quota, conflict, request-timeout, malformed-response, sign-out, concurrent-save and pending-journal scenarios.
- A simulated server commit with a lost response applied exactly once, retained one receipt, reconciled through the existing version precondition and did not duplicate payment records.
- Fresh-browser recovery retained pending edits and unrelated remote edits.
- The existing 23 October backup was checked entirely offline: 56 players, 35 sessions, 26 activities and 152 payment records. A player-note edit survived quota failure and recovery; all other records and financial totals were unchanged. Its successful delta save required three writes and no deletion.
- Local browser QA confirmed exactly three failed saves for an HTTP 503 outage, exactly one failed request for quota exhaustion, and recovery of the pending edit after reload. Synthetic data and local transport mocks remained outside Git and Hosting.
- Build and diff checks passed. Release gates require protected-main CI, a squash merge, identical candidate/merged trees, a build from the merged commit, Hosting-only deployment and live asset verification. Final evidence is recorded with the GitHub release and private operational record.

## Data And Release Boundaries

This deployment changes Firebase Hosting files only. It performs no production Firestore write, import, migration, rules, indexes, Functions, IAM or authentication configuration change. The verified 23 October restore point is retained; a fresh export is not attempted during the quota incident. Existing pending edits on user devices must not be cleared by release cleanup.

Normal authenticated app use will continue to save user edits after service availability returns. Deploying this fix does not itself reset the service quota.
